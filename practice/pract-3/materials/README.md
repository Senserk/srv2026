# Практическое занятие 3. Обнаружение атак по журналу событий

Курс 1 «Методы и принципы проектирования современных защищённых систем», день 3, занятие 2 (2 академических часа).

## Что вы сделаете

Пройдёте весь путь от чистой системы до обнаружения атаки:

1. создадите виртуальную машину с Ubuntu;
2. посмотрите, какие журналы система ведёт сама;
3. развернёте в Docker уязвимое веб-приложение;
4. последовательно пройдёте четыре атакующие миссии и увидите события в живой телеметрии;
5. разберёте журнал и напишете первое правило Sigma;
6. разработаете корреляционные правила и проверите их на контрольном сценарии;
7. настроите правило, снизив число ложных срабатываний.

Результат занятия: набор правил обнаружения, результаты их срабатываний и предложение по снижению ложных срабатываний (оформляются в отчёт по шаблону `report-template.md`).

Каждый шаг заканчивается **ожидаемым результатом** — сверяйтесь с ним, прежде чем идти дальше.

## Что понадобится

- Гипервизор на рабочем месте (VirtualBox или аналог) и установочный образ Ubuntu Server 24.04 (выдаёт преподаватель).
- Материалы практики (каталог `practice-3`) — переносятся на виртуальную машину по указанию преподавателя.
- Из программ на виртуальной машине: Docker и Python 3. Python входит в состав Ubuntu, Docker ставится на шаге 3.

После запуска стенда основная работа выполняется в браузере по адресу `http://localhost:8080`: команды `curl` для прохождения заданий не нужны.

## Шаг 1. Создание виртуальной машины (20 мин)

Установку можно начать и, пока она идёт, читать следующий шаг.

1. В гипервизоре создайте новую виртуальную машину: тип — Linux, версия — Ubuntu (64-bit), память — 2048 МБ, диск — 20 ГБ.
2. Подключите установочный образ Ubuntu Server к виртуальному приводу и запустите машину.
3. Пройдите установщик: раскладка по умолчанию, установка на весь диск, имя пользователя и пароль — на ваш выбор (запомните их). На экране «SSH Setup» включите **Install OpenSSH server**.
4. Дождитесь окончания установки, перезагрузите машину и войдите под своей учётной записью.

**Проверьте версию системы:**

```bash
lsb_release -d
```

**Ожидаемый результат:** строка вида `Description: Ubuntu 24.04 LTS`. Вы вошли в систему, виден приглашение командной строки.

## Шаг 2. Какие журналы ведёт система (8 мин)

Ubuntu регистрирует события безопасности ещё до установки каких-либо приложений. Посмотрим их.

**Последние события входа в систему (вход по SSH, смена пользователя):**

```bash
journalctl -n 20
sudo cat /var/log/auth.log | tail -n 20
```

**Создайте событие безопасности вручную — неудачный вход по `sudo` с неверным паролем:**

```bash
sudo -k            # забыть сохранённый пароль
sudo whoami        # введите НЕВЕРНЫЙ пароль один раз, затем верный
```

**Найдите эту неудачу в журнале:**

```bash
sudo grep "authentication failure" /var/log/auth.log | tail -n 3
```

**Ожидаемый результат:** в выводе есть строка с `authentication failure` и вашим именем пользователя. Это и есть событие безопасности, записанное операционной системой.

**Вопрос в отчёт (п. 1):** какое поле строки показывает, с какого терминала или адреса пришёл неудачный вход?

**Ожидаемый результат:** `docker compose ps` показывает контейнер `shop-app` в состоянии `Up`, а браузер — рабочую консоль исследователя, живую телеметрию и четыре миссии.

## Шаг 5. Журнал и первое правило обнаружения (10 мин)

Правило обнаружения — условие над записями журнала. Запишем его в формате Sigma. Начнём с простого правила по одиночному событию: кто-то отключил второй фактор аутентификации.

Команды ниже выполняются из каталога материалов практики. Перейдите в каталог проверки правил и создайте каталог для правил:

```bash
cd ../detect
mkdir -p rules
```

Создайте файл `rules/01_mfa.yml` со следующим содержимым:

```yaml
title: Отключение второго фактора без заявки
id: 00000000-0000-0000-0000-0000000000b1
name: mfa_disabled
logsource: {product: shop-app, service: auth}
detection:
    selection:
        event_type: auth.mfa.disable
        outcome: success
    filter_ticket:
        context.ticket_id|exists: true
    condition: selection and not filter_ticket
level: high
tags: [attack.credential-access, attack.t1556.006]
```

Правило срабатывает на событие `auth.mfa.disable`, кроме случаев, когда отключение оформлено заявкой (поле `context.ticket_id`).

Событие отключения MFA уже создано последней миссией шага 4. Примените правило:

```bash
python3 detect.py --events ../app/logs/events.jsonl --rules rules
```

**Ожидаемый результат:** программа выводит `сигналов: 1` и строку с названием правила «Отключение второго фактора без заявки».

## Шаг 6. Атака и её обнаружение (20 мин)

Теперь напишем правила для трёх атак и проверим их на настоящей активности.

### 6.1. Базовые правила

Корреляционные правила ссылаются на простые. Создайте файл `rules/00_base.yml`:

```yaml
title: Неудачный вход
id: 00000000-0000-0000-0000-0000000000a1
name: failed_login
logsource: {product: shop-app, service: auth}
detection:
    selection: {event_type: auth.login, outcome: failure}
    condition: selection
---
title: Успешный вход
id: 00000000-0000-0000-0000-0000000000a2
name: successful_login
logsource: {product: shop-app, service: auth}
detection:
    selection: {event_type: auth.login, outcome: success}
    condition: selection
```

### 6.2. Подбор пароля

Серия неудачных входов в одну учётную запись. Создайте `rules/02_bruteforce.yml`:

```yaml
title: Подбор пароля к учётной записи
id: 00000000-0000-0000-0000-0000000000b2
name: bruteforce_account
correlation:
    type: event_count          # считаем события
    rules: [failed_login]      # неудачные входы
    group-by: [actor.id]       # отдельно по каждой учётной записи
    timespan: 10m              # за 10 минут
    condition: {gte: 5}        # 5 и более
level: medium
tags: [attack.credential-access, attack.t1110.001]
```

### 6.3. Распыление паролей

Один адрес пробует один пароль против многих учётных записей. Создайте `rules/03_spraying.yml`:

```yaml
title: Распыление паролей с одного адреса
id: 00000000-0000-0000-0000-0000000000b3
name: password_spraying
correlation:
    type: value_count          # считаем РАЗНЫЕ значения поля
    rules: [failed_login]
    group-by: [source_ip]      # по адресу источника
    timespan: 30m
    condition: {field: actor.id, gte: 8}   # 8 и более разных учётных записей
level: high
tags: [attack.credential-access, attack.t1110.003]
```

### 6.4. Успешный вход после серии неудач

Признак успешного подбора. Создайте `rules/04_sequence.yml`:

```yaml
title: Успешный вход после серии неудачных попыток
id: 00000000-0000-0000-0000-0000000000b4
correlation:
    type: temporal_ordered     # события в заданном порядке
    rules: [failed_login_burst, successful_login]
    group-by: [actor.id]
    timespan: 15m
level: high
tags: [attack.initial-access, attack.t1078]
---
title: Три и более неудачных входа
id: 00000000-0000-0000-0000-0000000000b5
name: failed_login_burst
correlation:
    type: event_count
    rules: [failed_login]
    group-by: [actor.id]
    timespan: 10m
    condition: {gte: 3}
```

### 6.5. Получите контрольный журнал

Ручной журнал зависит от числа попыток. Нажмите **Сбросить стенд**, затем запустите детерминированный сценарий тех же атак вместе с обычной работой пользователей:

```bash
cd ../attack
python3 simulate.py --url http://localhost:8080
```

### 6.6. Примените все правила

```bash
cd ../detect
python3 detect.py --events ../app/logs/events.jsonl --rules rules --out alerts.jsonl
```

**Ожидаемый результат:** программа сообщает `Событий: 39` и `сигналов: 5`. Срабатывают правила подбора пароля (учётная запись `anna`), распыления (один адрес), отключения второго фактора и **два** срабатывания правила «успешный вход после серии неудач» — для `anna` и для `boris`. Эти же 39 событий видны на сайте.

**Вопрос в отчёт (п. 3):** какие правила сработали и для каких учётных записей или адресов? Для каждого сигнала укажите, истинный он или ложный.

## Шаг 7. Настройка и отчёт (7 мин)

Одно из срабатываний правила «успешный вход после серии неудач» — ложное: пользователь `boris` трижды ошибся в пароле и вошёл с четвёртой попытки (забыл пароль). Это не атака.

**Настройте правило:** в файле `rules/04_sequence.yml` поднимите порог серии неудач с 3 до 5 (`condition: {gte: 5}` во втором документе) и примените правила заново:

```bash
python3 detect.py --events ../app/logs/events.jsonl --rules rules
```

**Ожидаемый результат:** ложное срабатывание для `boris` исчезло; подбор пароля к `anna` (7 неудач) по-прежнему обнаруживается.

**Вопрос в отчёт (п. 4):** какова цена этого изменения — какую атаку правило теперь способно пропустить?

**Заполните отчёт** по шаблону `report-template.md` и сдайте его преподавателю вместе с каталогом `rules/`.

## Если что-то не получилось

- `docker compose ps` не показывает `Up` — посмотрите журнал контейнера: `docker compose logs`.
- `сигналов: 0` после атаки — проверьте, что создали `rules/00_base.yml`: без базовых правил корреляции не работают.
- Непонятная ошибка правила — проверьте отступы в YAML (ровно 4 пробела на уровень) и запустите `python3 detect.py` ещё раз: программа укажет файл с ошибкой.
